# Day 4 — CV Text Extraction with Gemini

## Part 0 — What Day 4 does, and where it starts from

By the end of Day 3, a user could upload a CV through Telegram and the bot would store the file — safely, under a UUID name, with the original filename kept in `cvs.file_name` — and say "got it." Nothing read the file. `cvs.raw_text` sat `NULL` on purpose; the Day 3 code comment on `CVRepository.create()` said so directly: *"raw_text is deliberately left NULL. Extraction is Day 4's job; Day 3 only proves the bytes arrived and are safe to keep."*

Day 4 is that job. Concretely: read the stored file, pull out its text, send that text to a language model (Gemini) and get back a structured profile — skills, experience, education, a summary — validate that structure, and store it. Do this without blocking the Telegram reply on it, since a network call to an LLM can take several seconds and nothing about *accepting* a file should make a user wait. Handle the case where there's nothing to read (a scanned PDF) without pretending it's the same as a broken file. And build it so that everything upstream of "give me a user_id and a session" knows nothing about Telegram, because the same extraction will eventually need to run from more than one place.

Two pieces of schema existed before this day started that anticipated this work almost exactly: the `cvs.raw_text` column, and the whole `cv_versions` table (`extracted_profile` JSONB, `extraction_model`, and an `embedding` column already wired to pgvector with an HNSW index). Day 4 didn't invent a shape for this data — it filled in a shape that was already there.

## Part 1 — The schema layer: `app/schemas/cv_profile.py`

This was the first file, by design, because it's the contract everything else has to agree to before it can be built. `app/schemas/` had existed since Day 1 as an empty placeholder; this is the first thing to live in it.

**Concept: what a schema is, here, that a DB model isn't.** `app/db/models/profile.py` already had `summary`, `total_experience_years`, `current_title`, `location`, `skills`, `experience`, `education` — a `Profile` ORM class describes a Postgres table. `CVProfile` in `app/schemas/cv_profile.py` describes something different: the shape of *whatever an LLM is allowed to hand back*. The two are similar on purpose — `CVProfile` is going to become a `Profile` — but they answer different questions, and they're declared independently rather than one being generated from the other. A DB column staying `JSONB` for flexibility and a schema field being tightened to a specific `list[ExperienceEntry]` are two different decisions that can move at different speeds.

**Concept: constrained decoding, and why validating afterward is still necessary.** Gemini's structured-output feature (`response_format`) sends a JSON Schema alongside the prompt. How strongly that schema binds the model is not something to assume — see Day 4.5, where a schema with no `required` list produced responses that dropped every array field without any error being raised. Treat `response_format` as a strong request, not a guarantee, and keep validating. But "the shape is right" and "the values are trustworthy" are different guarantees. A response can be syntactically perfect JSON matching the schema and still contain a hallucinated job title. `CVProfile.model_validate_json(...)` catches shape violations (a field of the wrong type, a missing required key); it does nothing about a plausible-sounding wrong fact, which no schema can catch. Both problems exist, and only the first one is this file's job.

**Decision: dates are free-text strings, not `date` objects.** Rejected alternative: a proper `datetime.date` field on `ExperienceEntry.start_date`/`end_date`. CVs write dates as "Jan 2022", "2022", "06/2021", "Present", "since last year." Forcing the model to emit ISO dates means one of two bad outcomes: it fabricates a specific date for something the CV only implied loosely, or the extraction fails outright on any CV that isn't precisely dated. Keeping dates as the original text preserves what the CV actually said. Turning that into a real date, if ever needed for sorting or duration math, is a separate, later, and optional step — one that can fail for one entry without invalidating the whole extraction. This is the same shape of decision as `OnboardingState` being a string column instead of a native enum: don't let a representation be more rigid than the real-world data it's describing.

## Part 2 — The database change: a fourth migration, and an autogenerate trap

**What was added.** Three columns on `cvs`: `extraction_status` (VARCHAR(32), default `'pending'`), `extraction_error` (nullable Text), `extracted_at` (nullable, timezone-aware DateTime). And an `ExtractionStatus` enum in Python — `PENDING`, `EXTRACTING`, `COMPLETE`, `FAILED`, `NO_TEXT_LAYER` — stored the same way `OnboardingState` is: a plain string column, not a native PostgreSQL enum type. The reasoning is copied verbatim from the Day 2c/2d precedent, because it's the same problem: a native enum type survives `downgrade()` as an orphaned type that has to be dropped by hand, and adding a sixth state later becomes an `ALTER TYPE` instead of an ordinary code change. Four migrations into this project, and this specific mistake has now been avoided four times by just... not making it.

**What went wrong on the first attempt, and why it mattered.** Running `alembic revision --autogenerate` produced a migration that, alongside the three real column additions, proposed *dropping* both HNSW indexes (`ix_cv_versions_embedding_hnsw`, `ix_jobs_embedding_hnsw`). Those indexes are real, they exist in the live database, and dropping them would have quietly degraded every future vector similarity query from an approximate-nearest-neighbor lookup to a full table scan — the kind of regression that wouldn't show up as an error, just as a slow query someone would have to debug months later with no memory of this migration being the cause.

The cause: those indexes were created in migration `563b5bb86690` with raw `op.execute("CREATE INDEX ... USING hnsw ...")`, because HNSW isn't expressible through SQLAlchemy's `Index()` the way a plain B-tree index is. That means they were never declared in `Base.metadata`. Autogenerate's whole method is comparing the live database against `Base.metadata` and proposing changes to reconcile them — so anything that exists in the database *but not in metadata* looks, from where autogenerate is standing, exactly like something that should be removed. It has no way to know the difference between "this was manually created and deliberately isn't tracked" and "this got deleted from the models and needs cleaning up."

**The fix, and the general lesson.** The generated migration file was hand-edited to remove the two spurious `drop_index`/`create_index` pairs, keeping only the three genuine `add_column`/`drop_column` operations. Autogenerate is a draft, not an instruction — reading the generated diff before running it, every time, is not optional caution here; it's the only thing standing between "add three columns" and "silently regress a vector search index." The down-up-down-up cycle was run and verified clean afterward, and the two HNSW indexes were confirmed still present in `pg_indexes` after the full cycle — not assumed, checked.

## Part 3 — Three new repositories: filling in what Day 3 hadn't needed yet

Day 3 shipped with `UserRepository` and `CVRepository`. Extraction touches three tables Day 3 never wrote to — `cv_versions`, `profiles`, `skills` — so three pieces of write access needed to exist before the orchestration logic could be built on top of them, keeping faith with the rule stated in `app/db/repositories/__init__.py`: nothing outside a repository writes SQL against a model.

**`CVRepository.create_version()`** — new method, not a new file. Computes the next version number as `MAX(version) for this cv_id, plus one`, via SQL's `func.max()` rather than `COUNT(*)`. The difference matters if a version is ever deleted: counting rows would let a freed version number get reissued and silently collide with anything that still references the old one by number; taking the max never reuses a number that's been used before, deleted or not.

**`app/db/repositories/profile.py` — `ProfileRepository`, new file.** `get_or_create(user_id)`, matching the shape of `UserRepository.get_or_create_preferences` from Day 3 almost exactly: check for an existing row, and if none exists, insert one with the JSONB list columns explicitly initialized to `[]` — not because the column default wouldn't handle it (it would), but because that's the existing convention in this codebase for exactly this situation, and matching it means the next reader doesn't have to wonder whether the omission was deliberate.

**`app/db/repositories/skill.py` — `SkillRepository`, new file, and `normalize_skill_name()`.** This is the "Option B" piece: CV skills feed the shared `skills` catalog via get-or-create on `normalized_name`, so that "Node.js" from one CV and "NodeJS" from another land on the same row instead of silently becoming two different skills that a later matching query (Day 6/7) would treat as unrelated.

`normalize_skill_name` lowercases, collapses whitespace, and then checks a small, explicit alias table — six entries: `node.js`→`nodejs`, `c++`→`cpp`, `c#`→`csharp`, `.net`→`dotnet`, `ci/cd`→`cicd`, `next.js`→`nextjs`. **Decision, with the rejected alternative stated explicitly because it was tempting:** this is not an attempt at a real synonym dictionary. Deciding whether "GCP" and "Google Cloud Platform" are the same skill, or whether "React" implies "JavaScript," is a fuzzy semantic problem that belongs to Day 6/7 matching, where there's a scoring model that can afford to be probabilistic about it. Folding punctuation variants of an *identical* skill name is not fuzzy — it's a deterministic cleanup of how humans type the same word — and conflating the two problems here would have meant building a half-a synonym system with no clear boundary on how big "a handful" should grow.

`get_or_create` uses the same `INSERT ... ON CONFLICT DO NOTHING` race-safety pattern as `UserRepository.get_or_create` from Day 3, for the same reason: two CVs can be extracted concurrently (a background task per upload, potentially several in flight), and two skills normalizing to the same key racing each other on insert must not raise `IntegrityError` — it should just mean one of them wins and both callers end up with the same row.

## Part 4 — `app/integrations/`: a new package, and the Gemini client

**Why a new top-level package instead of putting the Gemini client in `app/services/`.** The user who commissioned this called it directly: *"Days 6 and 7 both need outbound clients too, so the package earns its place."* The distinction being drawn is: a service owns business logic and talks to *this application's* database; an integration owns the shape of a conversation with something *outside* this application — an LLM provider today, a job board's API on Day 6, some other data source on Day 7. `app/integrations/gemini.py` is the only file in the entire codebase that imports `google.genai`. If Gemini were ever swapped for another provider, or a second provider added for comparison, the change is contained to this one file plus a new sibling — no service, no handler, no script would need to change, because they all depend on `GeminiClient.extract_profile(text) -> CVProfile`, not on how that answer was produced.

**Getting the model string right, instead of guessing.** `GEMINI_MODEL` in `app/core/config.py` is `gemini-3.7-flash`. That value did not come from training data — it came from fetching `ai.google.dev/gemini-api/docs/models` and cross-checking with a live web search, both during this session, both cited. This mattered enough to slow down for: an AI model's own knowledge of "the current model" decays the moment training stops, and this project is seven months past this assistant's own knowledge cutoff — long enough that the entire Gemini model lineage had moved (2.5 → 3.1 → 3.5 → 3.6 → 3.7 in that window). Writing `gemini-2.5-flash` from memory would have shipped a config value that was already wrong on day one, wrong in a way that would only surface as a confusing API error later, not as an obvious mistake anyone would catch on review.

**The API surface itself, and an honest gap in verification.** The same research turned up something more surprising than a version bump: the current Python SDK (`google-genai`) exposes a `client.interactions.create(model=..., input=..., response_format={...})` call, distinct from the `generate_content` pattern that existed in this assistant's training data. `EXTRACTION_PROMPT` is sent as `input`; `response_format` carries `CVProfile.model_json_schema()` so the model's output is constrained to that shape; the result comes back as `interaction.output_text`, a JSON string, parsed with `CVProfile.model_validate_json(...)`.

This code has **not** been executed against a real Gemini response. The credential handling rule adopted earlier in this project (never read, print, or verify `.env` — verify a credential by running something that depends on it and reporting only success or failure) meant the real test was left for the person holding the API key: `python -m scripts.extract_cv --user-id 2` was run this session and confirmed the pipeline works correctly right up to constructing the Gemini client, where it stopped on a clean, expected `ValueError: No API key was provided` — not a bug, a boundary. Everything before that point (finding the CV, reading it off disk, extracting its text) is verified. The shape of the actual Gemini call is verified only against documentation, not against a live response. That gap should close the first time this script is run with a real key configured — if the SDK surface turns out to have been misread, the fix is contained entirely to `app/integrations/gemini.py`.

**Decision: `asyncio.to_thread`, not a guessed async client.** Both doc fetches showed only the synchronous `client.interactions.create(...)`, with no confirmed async equivalent on this specific, very new API surface. Rather than guess at `client.aio.interactions.create(...)` — plausible, based on older `google-genai` versions having an `.aio` namespace, but unverified for this one — `extract_profile` wraps the synchronous call in `asyncio.to_thread`. This is correct regardless of whether an async surface exists: it moves the blocking network call off the event loop either way, and it doesn't require having correctly guessed a detail this session had no way to confirm.

## Part 5 — Reading the files themselves: `app/services/cv_text.py`

Separate from the LLM call entirely: turning the stored file's bytes into plain text is a local, offline, format-specific operation, using `pypdf` for PDF and `python-docx` for DOCX. `extract_raw_text(file_type, data) -> str` is deliberately "dumb" — it does the mechanical extraction and nothing else. In particular, an **empty string is a valid, ordinary return value**, not an error: a scanned PDF has no text layer, and that is a fact about the file, not a bug in the extractor. The decision about what an empty result *means* belongs one layer up, in `app/services/cv_extraction.py`.

**A test failure that corrected a wrong assumption.** The first version of this module's test suite tried to represent "a scanned PDF" using the same minimal, structurally incomplete PDF byte string that appears elsewhere in this project (`b"%PDF-1.4\n1 0 obj<</Type/Catalog>>endobj\ntrailer<</Root 1 0 R>>\n%%EOF"`) — good enough to pass a magic-byte check, since that's all it was ever built for. Feeding it to `pypdf.PdfReader` raised `PdfReadError: startxref not found` instead of parsing cleanly and returning no text. That's not a bug in `pypdf`; it's the correct behavior, and it exposed the actual distinction that matters: a **malformed** PDF (missing its cross-reference table entirely — not a file any real PDF producer would generate) is a different failure mode from a **well-formed PDF with a blank or image-only page** (a real scan). The extractor should let the first one raise — `extract_cv` catches it and marks the CV `FAILED`, correctly, because something about the file actually is wrong — and return `""` for the second, which `extract_cv` turns into `NO_TEXT_LAYER`, because nothing is wrong, there was just nothing to read.

The test was rebuilt using `pypdf.PdfWriter().add_blank_page(...)` to generate a genuinely well-formed but textless PDF, and a second test was added asserting the malformed case raises `pypdf.errors.PdfReadError` specifically — locking in the exact exception type, so a future `pypdf` upgrade that silently changed it would be caught by a test failure instead of surfacing later as a mysteriously uncategorized extraction.

## Part 6 — The orchestration function: `app/services/cv_extraction.py`

This is the function the rest of Day 4 exists to support: `extract_cv(user_id, session) -> ExtractionResult`. Steps: look up the user's latest CV; mark it `EXTRACTING`; read the file and extract its text; if empty, mark `NO_TEXT_LAYER` and stop; otherwise call Gemini; on success, write a new `CVVersion`, upsert the user's `Profile` from the result, and ensure every extracted skill exists in the `skills` catalog; mark the CV `COMPLETE`.

**Concept: who owns the transaction, and why it changes how errors must be handled.** Every database write in this codebase goes through `session_scope()` (from Day 3): a session opens, the caller's code runs, and — critically — the *caller's* `with` block is what commits, on normal exit, or rolls back, on any exception escaping it. `extract_cv` does not open its own session; it's handed one by its caller. That single fact has a sharp consequence: if `extract_cv` let a Gemini API error propagate up as a raised exception, the caller's `session_scope()` would catch it and roll back — and "roll back" doesn't mean "undo the Gemini call," it means "undo every write this function made in this transaction so far," *including* the `cv.extraction_status = FAILED` write meant to record that the extraction failed. The failure would vanish. The CV would revert to whatever status it had before the attempt — silently, with no record anything was ever tried.

This is why `extract_cv` catches its own **expected** failure modes internally — a bad or unreadable file, a `GeminiExtractionError` — and always returns normally, never raises for those. The bad-outcome write (`FAILED`, with the error message, with a timestamp) has to happen *and be allowed to commit*, which means the function has to survive its own failure and hand back a result instead of an exception.

**The other half of that decision: what's deliberately allowed to propagate.** Not every exception is caught. A bug in the profile-persisting code — a typo, a wrong attribute name, an actual programmer error — is left to propagate rather than being folded into the same `FAILED` status as "this CV had bad content" or "Gemini timed out." The reasoning: those are different categories of problem, and disguising a real bug as a routine, expected extraction failure would make it invisible. This showed up concretely in the one live run performed this session: `GeminiClient()`'s constructor raised `ValueError` for a missing API key — not a `GeminiExtractionError`, because that error class only wraps failures from an actual API *call*, and this was a configuration problem that happens before any call is attempted. That `ValueError` was, correctly, left to propagate. It crashed `scripts/extract_cv.py` loudly, with a full traceback pointing at the real cause — and the whole transaction rolled back cleanly, leaving the CV row exactly as it was (`pending`, confirmed by querying the database afterward), rather than marking a specific user's CV as failed when the actual problem was "this service isn't configured yet." A misconfiguration should be loud and should not look like one user's CV being unreadable.

**`ExtractionResult` as a return value.** A small frozen dataclass — `status`, optional `error` — handed back so a caller doesn't have to re-query the database to find out what just happened; it was already told, synchronously, in the same call. Both real callers use it: the background task decides whether to message the user, the manual script decides what to print.

## Part 7 — Wiring it into the bot, and a return-type change that rippled outward

**The signal problem.** The background task needs to know two things after a document upload: did this call actually create a new CV row (as opposed to being rejected for a bad extension, or never reaching the CV step), and whose user_id to run extraction for. Neither was available from `handle_document`'s old return type, a plain `BotReply` — and inferring "did it succeed" from the *wording* of the reply text would have been exactly the kind of brittle coupling this codebase has avoided everywhere else (`OnboardingState` existing at all is a direct rejection of that same class of mistake, just for conversation state instead of upload outcome).

**Decision: change `handle_document`'s return type to `DocumentOutcome(reply, stored, user_id)`.** A deliberate, explicit signal instead of an inferred one. `stored` is `True` only on the two code paths that actually call `CVRepository.create()` — a validation rejection, a mid-flow "finish the current question first" reply, and the "no user yet" fallback all leave it `False` by the dataclass's own default. `user_id` rides along specifically because handlers are not allowed to query repositories directly — `app/db/repositories/__init__.py` says so outright — so without it, the handler would have no legitimate way to learn which `user_id` to hand to `extract_cv`.

This is a return-type change, not an additive one, and it touched every existing caller: the real handler, and all three dry-run scripts (`onboarding_dryrun.py`, `onboarding_edgecases_dryrun.py`, `restart_resilience_dryrun.py`), each of which had to be updated to read `.reply` off the new result before passing it to their `show()` helper. All three were re-run after the change and produced identical output to before — the state machine itself didn't change, only what one method call handed back.

**Why `context.application.create_task`, not bare `asyncio.create_task`.** python-telegram-bot's own task-tracking method was used deliberately: passing `update=update` means an unexpected exception inside the background task gets routed through the same `error_handler` a normal handler exception would hit, rather than vanishing into asyncio's default "exception in a task nobody awaited" handling (a warning printed to stderr that's easy to miss and gives the user no feedback at all). This also happens to be the seam the user identified as making a real task queue (Celery, RQ, Cloud Tasks — "Option 4") a drop-in replacement later: `extract_cv(user_id, session)` itself has zero knowledge of *how* it was scheduled. Swapping an in-process background task for a real queue consumer touches only the small piece of code that calls it, never the orchestration function or anything beneath it.

**Deferred scope, stated explicitly rather than left implicit: no multimodal fallback.** A scanned PDF becomes `NO_TEXT_LAYER`, and the user gets told, in the same spirit as the existing oversized-file message from Day 3: *"I couldn't find any readable text in that CV — it looks like a scan. Try exporting a text PDF instead; I can't read scanned images yet."* Building OCR or a multimodal (image-understanding) fallback that could read a scan directly was a real option and was explicitly rejected for this day — not because it's a bad idea, but because it's a meaningfully bigger piece of work (a different Gemini call shape, image handling, different cost and latency characteristics) that deserves its own day rather than being folded quietly into this one. `NO_TEXT_LAYER` exists as its own status, distinct from `FAILED`, specifically so that this deferred work has an unambiguous set of rows to target later — "find every CV sitting at `no_text_layer`" is already, today, a complete and correct query for "here is the backlog once OCR exists."

## Part 8 — Dependencies: what got added, and one conflict resolved rather than ignored

Three new direct dependencies: `google-genai` (the Gemini SDK), `pypdf` (PDF text extraction), `python-docx` (DOCX text extraction). Rather than write version pins from memory into `requirements.txt`, all three were actually installed into the project's virtual environment and the *real, resolved* versions captured via `pip freeze` — the same "don't trust memory, check the real thing" principle applied to the Gemini model string, applied again here to package versions, which drift just as fast.

**The conflict that installing for real actually caught.** `google-genai` requires `websockets<17.0`; this project had `websockets==17.0.1` pinned (pulled in originally by `uvicorn[standard]`, which itself doesn't hard-require a specific version). Installing the new packages silently resolved `websockets` down to `16.1.1` to satisfy the constraint. That's exactly the kind of change that's easy to miss in a `pip install` and easy to regret later: a transitive downgrade to an *existing* dependency, not just new packages arriving. It was caught by diffing the full dependency tree before and after, rather than trusting that "it installed without an error" meant "nothing else changed." The downgrade was verified safe the concrete way — `pip check` reports no broken requirements, and nothing in this project opens a WebSocket connection of its own, so `uvicorn`'s WebSocket support (which is what actually needs the `websockets` package) is simply unused. It was kept, with a comment in `requirements.txt` explaining why the pin moved, instead of fighting the resolver to force the old version back and leaving `google-genai` broken.

## Part 9 — What was verified, and by what means

Every piece that doesn't need a live database or a live Gemini call has a `pytest` test: `CVProfile`'s defaults and nested serialization, `normalize_skill_name`'s alias folding and case-insensitivity, and `extract_raw_text` across a real generated DOCX, a real blank-page PDF, a malformed PDF, and an unsupported format. 45 tests pass total (34 carried over from Day 3, 11 new).

`extract_cv` itself is not covered by a `pytest` test, and that is a deliberate boundary carried over from Day 3, not an oversight: it writes to `cvs`, `cv_versions`, `profiles`, and `skills` through a real session, and this project's models use PostgreSQL-specific features — `JSONB`, pgvector's `Vector` type, HNSW indexes — that have no SQLite equivalent, so there is no lightweight in-memory way to test it. The established pattern for this class of behavior in this codebase is a live script run against the real database instead of a unit test — exactly how Day 3's restart resilience and edge cases were verified via `scripts/*_dryrun.py`, not `pytest`. `scripts/extract_cv.py` is that script for Day 4, and it was run this session against a real stored CV, confirming everything up to the Gemini call itself. The migration's own down-up-down-up cycle was verified clean, and — separately, because autogenerate had gotten it wrong once already this session — the two HNSW indexes were explicitly confirmed still present in `pg_indexes` afterward, not assumed from the migration file looking right.

## Part 10 — Transferable lessons

A few of these repeat lessons from Day 2c/2d/3 in a new context, which is itself worth noticing — the same handful of principles keep paying rent:

- **A schema or contract, written down before the code that fills it, is worth the detour.** `CVProfile` existing first is what let the Gemini client, the extraction orchestration, and the tests all agree on one shape without any of them having to guess at each other's expectations.
- **Constrained output from an external system is not the same as validated output.** Asking for a particular shape (via `response_format`) and checking *whether the values make sense* (via Pydantic validation, and eventually human review of extracted profiles) are two different jobs — and, as Day 4.5 found, the first one is weaker than it sounds, not just insufficient on its own. Skipping the second because the first exists is how a hallucinated job title ends up looking exactly as trustworthy as a real one.
- **Don't trust memory for anything that changes on a timescale shorter than the gap since training.** This applied twice in one day — a model identifier and a set of package versions — and both times the fix was the same: go look, don't recall.
- **Autogenerated migrations describe a diff against declared metadata, not against intent.** Anything created outside the ORM (a raw `CREATE INDEX ... USING hnsw`, here) is invisible to that diff and will be proposed for deletion the moment anything else in the same table changes. Reading the generated file is not optional.
- **Whoever commits the transaction determines how failure has to be handled underneath it.** `session_scope()`'s commit-on-exit design (Day 3) meant `extract_cv` couldn't just "let errors happen" the way code with its own try/except at the call site normally would — it had to actively distinguish failures worth recording (catch, mark `FAILED`, return normally) from failures worth surfacing loudly (let propagate, let the transaction roll back cleanly). Getting this backwards doesn't crash anything; it just quietly loses information, which is worse. Accurate for Day 4's single-session design; superseded by Fix 4 (Day 4.5), which moved the `FAILED` write into its own committed transaction so this distinction no longer has to be made inside a session someone else owns. The general lesson still holds — it just moved to a different seam.
- **A return value that requires the caller to infer meaning from wording is a bug waiting for the wording to change.** `DocumentOutcome.stored` exists because "did the upload succeed" needs to be a fact the service hands over, not a guess the handler makes by reading a success message's tone.
- **A downgrade in a dependency tree is still a change, even when nothing asked for it directly.** `pip install` doesn't announce "and by the way, this unrelated package moved" — diffing the full resolved tree is what catches it.

## Part 11 — Where things stand

Built and verified against the real database this session: the `extraction_status`/`extraction_error`/`extracted_at` migration (applied, cycled, and confirmed clean); `CVRepository.create_version`, `ProfileRepository`, `SkillRepository`; the file-format text extractors for PDF and DOCX; the full `extract_cv` orchestration, exercised live through the point where a missing API key raises before any network call, and the surrounding transaction rolls back cleanly; the Telegram-side wiring (`DocumentOutcome`, the background task, the two new user-facing messages for `NO_TEXT_LAYER` and `FAILED`); all three pre-existing dry-run scripts confirmed still passing after the `handle_document` return-type change; 45 passing tests.

**Amended after Day 4.5.** `app/integrations/gemini.py` has now been executed against the live API, against a real CV, end to end. What the run established:

- The call shape was correct as written. `interactions.create` with a `model`, a string `input`, and a `response_format` dict was accepted, and a valid `CVProfile` came back. The pre-flight concern that Pydantic's `schema_` alias might need to be sent as `schema_` rather than `schema` was unfounded: a plain dict is an accepted member of the `response_format` union and passes through with the correct wire key.
- **The response schema was too weak.** The first live run returned `status=complete` with every array field empty, because `CVProfile.model_json_schema()` emits no `required` list when every field has a default. `_build_response_schema()` now marks fields required and inlines `$defs`; the same CV then returned 39 skills, 3 roles and 1 degree.
- **A server-side failure does not raise.** It returns a well-formed `Interaction` with `status='failed'` and `output_text=None`. Day 4's code passed that `None` straight to `model_validate_json()`, which does end as a `GeminiExtractionError` — but one reading *"JSON input should be string, bytes or bytearray"*, pointing at our schema when the cause was the provider's. Status guards were added.
- **The SDK's async surface exists and takes a timeout.** `client.aio.interactions.create` is a genuine coroutine function accepting `timeout: float | httpx.Timeout`, which is what let Fix 4 put a real deadline on the call instead of an uncancellable `asyncio.to_thread`. Measured against the sync path on the same CV, the two behave identically.
- **The default retry policy retries 429.** An exhausted daily quota consumed the full request timeout in exponential backoff and then reported itself as a client-side timeout, sending an entire debugging session after the wrong layer. `HttpRetryOptions` now excludes 429 from the retried status codes.
