## Stage notes

**CV text + profile — STAND-IN.** The text layer extraction is real:
`python-docx` read 383 characters out of a 36,855-byte file, and the
stand-in received them. Only `extract_profile` was substituted. The
claim/release protocol, the `cv_versions` insert, the emptiness check,
the supersession check and the skill catalog writes all ran.

**Profile persisted — REAL.** `experience=1.20y` is computed by
`compute_total_experience_years` from the structured start/end fields,
not taken from the model. That is deliberate: a number the model
produced could not be explained to a user asking "why 1.2 years?".

**Jobs ingested — REAL.** Six records in, six accounted for. Note
`inserted=3` against four valid-looking postings: `ml-1-repost` has the
same title, company and location as `ml-1`, so `compute_content_hash`
produced the same hash and it was recognised as a repost. `last_seen_at`
was refreshed on the original rather than a second row being created.

**Funnel balanced — REAL.** `normalize_failed + validation_failed +
filtered_out + duplicates + inserted == records_fetched`. Asserted, not
computed to be true.

**pgvector retrieval — REAL.** `similarity=0.9976` is
`cos(4°) = 0.99756`, the angle the fixture put job 1 at. The number
being _predictable_ is the point: it would catch a distance-to-similarity
conversion getting inverted, which would still return three rows in a
plausible order.

**Scoring + ranking — REAL.** `max=1.0000` because the fixture is
generous — job 1 has every skill the profile lists, an experience range
containing 1.2 years, an exact location match and a title matching a
target role. On live data no pair looks like this.

**LangGraph run — REAL.** `branch=notify`. This branch does not execute
on the project's live data, where `notify_eligible` is 0 because
`weight_covered` sits at 0.50 against a floor of 0.55. Here skills and
experience bounds are present, coverage reaches 1.0, and the branch is
entered for real.

**Telegram delivery — STAND-IN.** The attempt row was opened, the
message rendered, `mark_sent` ran and the partial unique index accepted
one `SENT` row. No socket was opened. `--with-telegram` uses the real
notifier.

**Duplicate suppressed — REAL.** The second selection returned zero
candidates: `sent_job_ids` excluded the job before the delivery loop.
This is the Day 11 attempt-table design working — at most one `SENT`
row per `(user, job)`, any number of `pending`/`failed`.

### Can one user be traced from CV upload to feedback?

Yes, in one join path:

```text
users.id = 1
  -> cvs.user_id = 1                         (extraction_status = 'complete')
  -> cv_versions.cv_id = 1                   (version 1, embedding NOT NULL)
  -> profiles.user_id = 1                    (active_cv_version_id = 1)
  -> recommendations.user_id = 1             (3 rows, ranks 1-3, scoring_run_id = 1)
  -> notifications.user_id = 1               (status = SENT, recommendation_id set)
  -> user_feedback.user_id = 1               (action = interested)
```

Every hop is a real foreign key. `agent_runs.id = 1` records the run
that produced the recommendations, with `started_at` before and
`finished_at` after.

### Verified about that state

|                           |                                                                                        |
| ------------------------- | -------------------------------------------------------------------------------------- |
| Foreign keys              | All resolve; no orphans                                                                |
| Timestamps                | `started_at` < `finished_at` on both run tables; `sent_at` after the recommendation    |
| Status transitions        | `pending` → `complete` on the CV; `PENDING` → `SENT` on the notification               |
| Abstains                  | `skill_score` NULL on jobs 2 and 3 — never 0.0                                         |
| No unexpected duplication | 3 jobs from 6 records; 3 recommendations from 2 scoring passes in the idempotency test |
| Rejections auditable      | 2 `ingestion_rejects` rows, each with a reason and the raw payload                     |

## What this run does not establish

- **Adzuna, Gemini and Telegram were not contacted.** Three stages are
  marked STAND-IN above and that marking is the honest boundary of this
  trace. See `docs/TEST_RESULTS.md`.
- **The scores are flattering.** A fixture built to clear the gates
  clears them. This proves the notify path _works_, not that it fires
  usefully on real postings — on live data it has fired zero times.
- **This was a single run on an empty database.** No concurrency, no
  accumulated state, no quota exhaustion, no partially-failed run.
- **370 ms is not a production latency figure.** It excludes every
  network call, which is where essentially all real time goes: a full
  enrichment pass is 27–84 minutes against Gemini's free tier.
