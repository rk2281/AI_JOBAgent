## Why two tasks and not a day-of-week branch

A conditional inside one script — "run ingestion only if today is
Sunday" — fails the `CLAUDE.md` §0 test directly: a broken conditional
still produces a normal-looking `agent_*.log` and a normal `agent_runs`
row every single night, because the run itself completes and reports a
status. Nothing about that log or that row is structurally different
from a correctly-behaving one; the only way to notice the conditional
had rotted would be reading the log's contents on the one day a week
it matters, by hand, forever.

Two tasks make the two cadences a property of the registration itself,
not of code running inside one process. `Get-ScheduledTaskInfo
-TaskName "AIJobHuntAgentIngestion"` on its own — no log parsing, no
date-math — reports whether the weekly trigger exists and whether it
has ever fired, independent of whatever the nightly task did that same
night. That is the same shape as the funnel counters this project
already insists on: a number a human can read, rather than a branch a
human has to trust.

This also mirrors a separation the codebase already makes for a
related reason: ingestion, embedding and enrichment are three separate
services (`run_ingestion`, `run_job_embedding`, `run_enrichment`)
because they are rationed by different quotas — Adzuna for ingestion,
`gemini-embedding-001` for embedding, `gemini-3.6-flash` for
enrichment (the last two confirmed on separate quota buckets, per
`CLAUDE.md` §10 Day 13, "Closed"). Splitting _scheduling_ cadence along
the same ingestion/enrichment line follows the same logic the code
already follows for _quota_.

## The half-state, and what it teaches

`schedule_agent.ps1` writes the runner files before it registers
anything — verified by reading the script this session. In the
non-`-SelfTest` path: `Write-Runner` is called for both
`$NightlyRunner` and `$WeeklyRunner` (lines 340–341) _before_
`Register-AgentTask` is called for either task (lines 346, 352). The
`-SelfTest` path (lines 306–309) calls `Write-Runner` for both files
too, and then explicitly registers nothing (`"registered nothing
(self-test arms no task)"`, line 335). So writing the runner files and
registering a task are not one operation in this script; they are two,
and only the first one is guaranteed to happen.

Today, 2026-09-06, `Register-ScheduledTask` is reported to have failed
with `Access is denied (HRESULT 0x80070005)` while registering the two
split tasks — a different incident from the `2026-09-05` S4U
registration failure already recorded in `CLAUDE.md` §1, even though
the error code is identical. **I did not observe today's failure
through this session's own tool output — it was reported to me, not
run in front of me** — so I am naming it as reported, not as a fact
this session verified directly.

What this session _did_ verify directly, is the state that failure is
reported to have left behind:

- `run_nightly.ps1` and `run_weekly_ingestion.ps1` both existed on disk
  with `LastWriteTime 06-09-2026 12:20:49` (read this session, Stage
  2a), already carrying `--skip-ingestion` and `--skip-enrichment`
  respectively (`Select-String`, same stage).
- By the time this session queried live tasks (Stage 2b),
  `AIJobHuntAgentIngestion` existed and was registered (`State Ready`,
  `LogonType S4U`). Whether it was _absent_ specifically at the
  12:20:49 write is the reported account, not something this session
  independently queried — Stage 2a's scheduled-task check covered only
  `AIJobHuntAgent`, not `AIJobHuntAgentIngestion`.
- Taking the reported account at face value: for some window today,
  `run_nightly.ps1` already carried `--skip-ingestion` while no weekly
  task existed to run `run_weekly_ingestion.ps1` — meaning ingestion
  was off entirely, neither nightly nor weekly, until registration was
  retried and succeeded (evidenced by `AIJobHuntAgentIngestion` now
  being `Ready` with a real `NextRunTime`, and by the file's second
  `LastWriteTime`, `12:50:53`, read this session, Stage 2b).

The difference between the two incidents is the lesson. On
2026-09-05, the registration failure left nothing behind, because the
runner file being registered had not changed shape from the one
already live — the old task kept doing what it had always done. On
2026-09-06, the same failure left a state nobody chose, because
`Write-Runner` had already changed what the _existing, still-running_
nightly task would do the next time it fired, before the _new_ task
that was supposed to cover the gap existed. Same error, different
blast radius. **"The failed attempt changed nothing" was a true
statement about the object that failed to register. It was not a true
statement about the object that already carries the behaviour** — the
runner file — which had changed regardless of whether registration
succeeded.

## What ingestion cadence does and does not do

`app/services/job_ingestion.py`'s imports (read this session):
`app.integrations.adzuna` only; no Gemini import anywhere in the file.
`app/workflows/nodes.py`'s `discover_jobs` (read this session) calls
`AdzunaClient()` and `run_ingestion(...)` only — no enrichment or
embedding call inside it. So ingestion talks to Adzuna and nothing
else.

Stated plainly because it bears directly on tonight: **skipping
ingestion frees zero `gemini-3.6-flash` (enrichment) quota.** The split
stops the unenriched pile from growing on the nights ingestion is
skipped. It does not do anything to drain the pile that already
exists.

`list_needing_enrichment` (`app/db/repositories/job.py`, read this
session) orders by `Job.id` ascending. Its docstring states the reason
directly: _"Ordered by id, oldest first, so an interrupted run resumes
predictably rather than reshuffling which rows are left."_ Combined
with the per-run numbers already read this session from `agent_runs`
(reported as printed, not computed against each other):

| run id | `jobs_inserted` | `jobs_enriched` |
| ------ | --------------- | --------------- |
| 5      | 0               | 5               |
| 6      | 100             | 17              |
| 7      | 100             | 1               |

— the newest-ingested jobs are the ones sitting furthest back in an
oldest-first enrichment queue. No claim is made here about whether the
backlog converges; that would require a rate, and no rate was
computed.
